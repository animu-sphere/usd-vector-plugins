# Release provenance and lock verification dogfooding

- Date: 2026-09-06
- Consumer revision: `e811359` on `main`
- OST version exercised locally: `ost 0.22.8`
- Runtime: `openstrata-cy2026-windows-x86_64-py313-usd`
- OpenUSD: 26.08
- Platform: Windows x86_64
- Toolchain: MSVC toolset 143, Python 3.13
- Scope: why a packaged and validated `plugin-product` was rejected by a
  downstream composition, and which OpenStrata gates did not catch it

This is an engineering dogfooding record for the release path, not the plugin.
It follows [report 01](01-2026-09-02-v0.22.8-geojson-fileformat-dogfooding.md),
which covered the bundle itself.

## TL;DR

`usd-vector-plugins` 0.1.0 was packaged against a hand-placed OpenUSD tree
instead of the OpenStrata-managed runtime named by its own `strata.lock`. The
resulting product records runtime identity `sha256:ce996432…`, which exists in
no registry, and `usd-geospatial-runtime` refused to compose it.

Every pin in the repository source was already correct. OpenStrata packaged,
validated, and reported success on the mismatched product anyway. Two gates
that could have stopped it did not:

- `ost package` / `ost validate` never compare the product's
  `provenance.runtime.digest` against the project's `strata.lock`. The product
  was recorded as `provenance.runtime.source: "local"` and
  `build_outputs.origin: "ost-managed"` with `validation.passed: true`
  simultaneously.
- `ost lock --check` does report failure on this tree, but for the wrong
  reason: it compares the lockfile **byte-wise**, so it fails on JSON
  formatting while the runtime digest is identical. That false negative makes
  it unusable as a CI gate and pushes developers toward `ost lock`, which
  rewrites the digest to whatever runtime is active. That is the drift
  mechanism, and it has already reproduced in a sibling repository.

Both are recorded below as asks. Neither required an OpenStrata source change
to work around; the repository can gate this itself, and will.

## 3. Findings

### 3.1 A packaged product can record a runtime absent from the lock and still validate

The 0.1.0 product manifest carries:

```json
"provenance": {
  "build_outputs": {
    "detail": "all 4 package-relevant output(s) match the last managed build",
    "origin": "ost-managed",
    "override_accepted": false,
    "status": "matched"
  },
  "runtime": {
    "digest": "sha256:ce9964320b5ab83b6f124b307af419340d342f6741fdf5fd1964e712243727a1",
    "id": "openstrata-cy2026-windows-x86_64-py313-usd",
    "source": "local",
    "validation": "passed"
  },
  "validation": { "members": 1, "passed": true }
}
```

The project's `strata.lock`, in the same tree, names
`sha256:3a4e399351763a5ef55575e5341b28adabf1ffe6cf55a1d3cc315e19aba9dbff`. The
local registry holds exactly one `usd`-profile runtime, and it is that one.
`sha256:ce996432…` is not in the store and not in any published registry.

Its origin is visible in the product stage's
`bundles/vector-geojson/validation/environment.json`:

```json
{ "key": "PATH",              "value": "C:/usd/openusd-26.08-cy2026/bin" }
{ "key": "CMAKE_PREFIX_PATH", "value": "C:/usd/openusd-26.08-cy2026" }
{ "key": "PXR_PLUGINPATH_NAME", "value": "C:/usd/openusd-26.08-cy2026/plugin/usd" }
```

A hand-placed OpenUSD tree was on the environment when the product was
packaged. OpenStrata adopted it as a `local` runtime, hashed it, and proceeded.

The `id` field is the sharp edge. The ad-hoc tree was recorded under the
**same runtime id** as the managed runtime,
`openstrata-cy2026-windows-x86_64-py313-usd`, with a different digest. Any
consumer reading the id alone sees agreement; only the digest reveals the
substitution.

Note also that `build_outputs.origin` reports `ost-managed` and
`override_accepted` is `false`. Read together with `runtime.source: "local"`,
the manifest simultaneously asserts a managed build and an unmanaged runtime.

**Ask (P1).** When a project has a `strata.lock`, `ost package` and
`ost validate` should compare the resolved runtime digest against
`strata.lock`'s `runtime.digest` and fail, or at minimum warn loudly, on
mismatch. A `source: "local"` runtime carrying a managed runtime's `id` with a
non-registry digest is the specific case worth refusing. Today the product
that results is well-formed, passes `ost artifact verify`, carries a valid
SBOM, and is still not composable — the failure surfaces only in a downstream
consumer that happens to compare runtime identities.

### 3.2 `ost lock --check` fails on formatting, not on content

On this tree:

```json
{
  "data": { "lock": "strata.lock", "up_to_date": false },
  "ok": false,
  "redacted": true,
  "schema": 1,
  "warnings": []
}
```

This looks like the drift being caught. It is not. Regenerating the lock into a
scratch copy and diffing against the committed file gives exactly one
difference — JSON array formatting:

```diff
-      "features": ["core"]
+      "features": [
+        "core"
+      ]
```

The `runtime.digest` is byte-identical. `up_to_date: false` here means only
that the committed file was not serialized by this `ost` version's writer.

Two consequences:

1. `ost lock --check` cannot be wired into CI as a drift gate, because it
   reports failure on a correct lockfile. Its signal carries no information
   about whether the pinned runtime still matches.
2. The natural response to a failing `--check` is to run `ost lock`. That
   regenerates the lockfile from **whatever runtime is currently resolvable**.
   On a machine with a leaked `CMAKE_PREFIX_PATH`, this silently rewrites
   `runtime.digest` to the ad-hoc tree's identity.

Consequence 2 is not hypothetical. The sibling `usd-raster-plugins` repository
now has `sha256:ce996432…` committed in its `strata.lock`, while its published
0.1.0 product still correctly records `sha256:3a4e3993…`. The drift entered
through the lockfile there and has not yet reached an artifact.

**Ask (P2).** `ost lock --check` should compare lock **content**, not bytes:
parse both and compare the resolved fields, or normalize before comparing. A
formatting-only difference should either pass or be reported distinctly from a
digest change, so that CI can gate on the one that matters.

### 3.3 `ost lock --check` exit code does not match its documented value

`ost lock --help` states that `--check` exits 1 when the lock is not up to
date. The observed exit code is 5.

```text
$ ost lock --check --json --redact-paths ; echo $?
5
```

**Ask (P3).** Align the help text with the implementation, or document the exit
code table. Scripts written against the documented value will treat 5 as an
unexpected crash rather than a clean "not up to date" result.

## 4. What worked well

- `--redact-paths` is genuinely useful. Every JSON excerpt in this report was
  produced with it, and it made attaching real command output to a public
  record a non-decision. The `openstrata.redaction/v1` schema marker in the
  output is a good touch.
- `ost artifact push` being named "the producer verb", verifying a pinned
  destination digest against the computed manifest digest, and enforcing
  publisher identity through `openstrata-artifact-policy.toml`, is exactly the
  shape needed to move this repository's publish step out of a developer shell
  and into CI. The missing publish automation is a repository-side gap, not an
  OpenStrata one.
- `ost artifact verify` correctly passed on the 0.1.0 product. The artifact is
  internally sound; only its runtime provenance is wrong. Keeping those two
  concerns separable made the diagnosis quick.
- The composition's rejection was actionable because the manifest recorded the
  runtime digest at all. The provenance block had the answer in it.

## 5. Repository-side response

None of the above blocks this repository, and no OpenStrata source change is
required for it to proceed. The planned response is recorded in
[RELEASE_PLAN_v0.2.0.md](../../roadmap/RELEASE_PLAN_v0.2.0.md):

- extend `tools/check_release_metadata.py` to assert that a packaged product's
  `provenance.runtime.digest` equals `strata.lock`'s `runtime.digest` and that
  `provenance.runtime.source` is not `local`;
- move the OCI publish into the tag-triggered workflow using
  `ost artifact push`, so no artifact is published from a developer machine;
- republish as 0.2.0, since 0.1.0's digest is already taken.

The first item is a local reimplementation of the P1 ask. If OpenStrata adopts
that gate, the repository check becomes redundant and will be dropped.
