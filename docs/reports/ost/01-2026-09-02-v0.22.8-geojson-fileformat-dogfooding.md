# GeoJSON FileFormat bundle dogfooding

- Date: 2026-09-02
- Consumer revision: `85b58ac` on `main`
- OST version exercised locally: `ost 0.22.8`
- Template: `usd-fileformat-cpp` 1.2.1
- Runtime: `openstrata-cy2026-windows-x86_64-py313-usd`
- OpenUSD: 26.08
- Platform: Windows x86_64
- Toolchain: MSVC toolset 143, Python 3.13
- Scope: connect the GeoJSON reader and authoring libraries as a real
  OpenStrata FileFormat bundle and exercise the generated template workflow

This is an engineering dogfooding record for `plugins/vector-geojson`. The
bundle is intentionally built from the generated `usd-fileformat-cpp` template,
with the generated helper copied into the bundle so standalone CMake builds do
not depend on an OpenStrata checkout.

## TL;DR

The first runtime pass exposed several integration failures at the repository
boundaries. None required an OpenStrata source change. The bundle manifest,
standalone library composition, OpenUSD 26.08 adapter calls, and USDA string
serialization were corrected locally. After those fixes, the pinned workflow
passed plugin L0-L5, the workspace graph check, and all three CTest suites.

One OpenStrata behavior remains worth recording: `ost build` emits a warning
when the plugin was already built through `ost plugin build` and its unchanged
outputs do not have matching root-build provenance. This is non-blocking, but a
clearer attribution mechanism would make mixed workspace/plugin workflows less
surprising.

## 3. Failures found and repository-side fixes

### 3.1 Bundle manifest contract

The initial bundle did not have a stable valid OpenStrata plugin manifest. An
empty `release_members` entry was also rejected. The final manifest declares
`vector-geojson`, kind `usd-fileformat`, the OpenUSD compatibility range
`>=26.08,<27.0`, the `usd-fileformat:geojson` capability, plugInfo location,
and smoke, roundtrip, and negative fixtures.

The source now keeps the generator provenance in
`openstrata.scaffold.yaml`:

```yaml
template:
  id: usd-fileformat-cpp
  version: 1.2.1
generator:
  name: ost
  version: 0.22.8
```

### 3.2 Standalone plugin build and library composition

The first standalone plugin build could not find the project-owned library
targets. The bundle now follows the working generated-bundle pattern: it adds
sibling libraries only when their targets are not already present. The three
plain libraries also provide installable CMake package config/version files, so
the same targets work both from the workspace and from a standalone bundle
configure.

### 3.3 OpenUSD 26.08 adapter compatibility

Compilation against the pinned runtime exposed adapter-level API mismatches.
The repository-side fixes were:

- include `pxr/usd/ar/asset.h` for the `ArAsset` overload;
- use `ArGetResolver()` for resolver access;
- dereference `UsdStageRefPtr` before accessing its root layer;
- use the OpenUSD 26.08 `SdfFileFormat` constructor order;
- register `SDF_DEFINE_FILE_FORMAT` inside `TF_REGISTRY_FUNCTION(TfType)`;
- treat `SetCustomDataByKey` as a `void` API.

These are source compatibility fixes for the pinned SDK, not OST defects.

### 3.4 L3 `usdcat.read` emitted empty stdout

The initial L3 failure had an empty stderr and an empty `usdcat` stdout, even
though `usdcat -o output.usda` and Python `Usd.Stage.Open()` succeeded. The
OpenStrata L3 harness invokes `usdcat` with the fixture identifier and checks
that the command emits USDA text. The custom GeoJSON format had a reader but no
`WriteToString` implementation, so the layer could be read but not serialized
to stdout through the custom format.

The file format now delegates `WriteToString` to OpenUSD's USDA format. The
same L3 command then passed, and L5 flattened output matched both checked-in
golden fixtures.

## 4. OpenStrata behavior worth following up

When `ost plugin build` is run first and `ost build` later sees the plugin's
outputs unchanged, `ost build` reported:

```text
warning: did not attribute 3 unchanged workspace output(s) without matching
prior root-build evidence: plugins/vector-geojson/lib/..., .../plugInfo.json,
.../plugInfo.json.in
```

The root workspace build and all tests still completed successfully. The
warning appears to describe provenance ownership rather than a stale or
incorrect artifact. A future OST version could either recognize prior
successful plugin-build evidence or explain the mixed-build attribution rule
more explicitly. This is recorded as an informational P3 ask, not a blocker.

## 5. Follow-up coverage

The bundle contract now includes:

- `basic.geojson` for the canonical extension;
- `basic.json` for a GeoJSON document using the generic JSON extension;
- `invalid.geojson` for invalid GeoJSON geometry;
- `unrelated.json` for generic JSON rejection;
- flattened golden fixtures for both valid source forms.

The current runtime checks exercise discovery, resolver-backed reads, USDA
serialization, Python stage opening, and golden flattening. Broader resolver
implementations, cross-platform runtime matrices, and streaming performance
remain outside this dogfooding pass.
